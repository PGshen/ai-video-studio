# manim（Manim Community）

## ✅ 已验证：`add_sound()` 会给整段视频套一层至少 1 秒的静音音轨，短镜头的成片时长会被垫到 ~1.02s

日期：2026-09-28（M2 T2 自验证时发现）。来源：实测（manim 0.21.0 源码
`manim/scene/scene_file_writer.py` 的 `SceneFileWriter.create_audio_segment`/
`add_audio_segment`）+ 本地渲染脚本验证。

`Scene.add_sound()` 最终调用 `SceneFileWriter.add_sound()` → `add_audio_segment()`。
第一次调用时，`create_audio_segment()` 会先建一条**默认 1000ms 的静音音轨**
（`pydub.AudioSegment.silent()`，不传 `duration` 参数时 pydub 的默认值就是
1000ms），后续每次 `add_sound()` 只是把真实音频 `overlay` 到这条底轨上、
必要时向后延长；如果新音频结束时刻仍在 1000ms 以内，底轨长度**不会缩短**，
仍然是 1.0s。最终合成视频按这条音轨的长度混流，即使所有镜头的 `wait()`
加起来远小于 1 秒，输出视频也会被垫到 ~1.0s + 一点编码器帧对齐的余量
（本地实测稳定在 1.024s 左右，猜测是 AAC 每帧 1024 采样点在某个采样率下的
对齐量，未继续深挖）。

**验证脚本**：两个镜头各 `self.add_sound(...)` 一段 0.4s 静音 wav + `self.wait(0.4)`，
`resolution=(480,270)`、`fps=15`；期望总时长 0.8s，实测 `ffprobe` 读到 1.024s。
把declared 总时长提到 1.2s（3 个 0.4s 镜头）之后，实测 1.237s——只比声明值多
一点点（编码器帧对齐），说明"底轨最短 1 秒"是唯一的异常来源，不是每镜头都
有的固定开销。

**影响范围**：
- `render_preview`（T2）用"更早镜头声明的音频时长之和"推算目标镜头在合并视频
  里的起始偏移——只要**全部镜头声明的音频总时长 ≥ 1 秒**，这个底轨异常就不会
  触发，偏移计算就是准的。真实叙事音频（一句旁白通常几秒）基本不会踩到这个
  下限；只有像单测里那种几百毫秒的合成静音片段才会踩到。
- worker 的成片渲染（T5）同理：只要每个镜头的旁白时长不低于 1 秒（正常
  语音场景几乎总是满足），"渲染出的镜头时长 = 声明的音频时长"这个不变量就
  站得住；如果未来出现"极短镜头"（<1s 旁白）的产品需求，这里需要重新评估。

**测试写法**：涉及 `render`/`render_preview` 的自动化测试如果用脚本生成的合成
音频（T4 fixture 同款做法），**声明时长要 ≥ 1.0s**，否则实测出来的视频总时长
会比预期长，断言会跟着不稳。
