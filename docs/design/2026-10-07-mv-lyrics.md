# 音乐 MV 的歌词联动

状态：待批准（2026-10-07）。本文是对 [produce 阶段设计](2026-10-06-produce-stage.md) 与 [导入音乐与 MV 设计](2026-10-05-import-music-mv.md) 的**补充**：只增加歌词这一路输入与相关的创意、制作、前端环节，不改变两阶段流水线（`concept → produce`）。已批准的旧文档不修改。

## 1. 背景与目标

`produce` 阶段上线后跑通了 MV 的真实冒烟，但成片效果差：5 分钟的歌只有一个橙色光点从小长大，画面和歌词没有任何关系，前 95 秒几乎是纯黑。负责人给了一个参考视频（纯代码渲染的 MV，162 秒），拆解后的差距：

- 参考视频的**内容跟着歌词走**：每句歌词对应一个具体画面（「凌晨三点 机房亮着光」→ 机架线框图，「喝光一条江的水」→ 数字滚轮飞转，「小数点又挪了一位」→ 整屏橙底的大字「小」）。画面是信息图、字体、数据可视化的组合，统一在近黑底、一种橙色、细线与网格的视觉语言里。
- 节奏是连续变形加少数爆点：镜头检测显示硬切很少，只在段落转换处有密集闪切；关键字在拍点上出现。
- 我们的模型**拿不到歌词，也听不到歌**。它能用 `beat`/`downbeat` 事件对拍，但不知道每句歌词在第几秒唱，所以做不出「歌词 → 画面」。

**目标**：用户在「创意与要求」阶段提供带时间戳的歌词（LRC）；系统把它变成客观事实（每句的文字与起止时间）交给模型；创意阶段由人确认「歌词意象」，制作阶段由模型自己决定怎么画、怎么对齐拍点。系统仍然不替模型排镜头、不设网格。

**不做**：自动识别歌词（语音识别）、没有时间戳的纯文本歌词、双语翻译（字幕要不要英文，由负责人在简报里写）、歌词编辑器、逐字时间（只按行用）、旧项目兼容。

## 2. 已确认的决定

| 项 | 决定 |
|---|---|
| 歌词来源 | 用户上传 `.lrc` 文件，与歌曲一起在「创意与要求」阶段上传；只收带时间戳的 LRC |
| 歌词是否必填 | 可选：没有歌词时 MV 与现在完全一致 |
| 歌词意象归属 | 创意阶段决定、人确认：简报新增「歌词意象」章节；制作阶段照着执行 |
| 字幕与关键字 | 模型自己画；系统只给歌词数据，只做检查，不叠字幕 |
| 精度 | 按行，不做逐字；时间准不准取决于用户的 LRC |

## 3. 数据：歌词作为客观事实

### 3.1 文件与解析

- 文件：`music/lyrics.lrc`，**只能由上传接口写入**（工具托管，模型不能改）。位置与 `music/source.*` 并列，`music_source == "import"` 的项目才有。
- 解析规则：
  - `[mm:ss.xx]歌词`，秒的小数位可为 1–3 位；一行可有多个时间戳（每个时间戳各成一句）。
  - `[offset:毫秒]` 生效（正数让歌词提前，与通行 LRC 一致）。
  - 其他元信息标签（`[ti:]`、`[ar:]`、`[al:]`、`[by:]`、`[length:]` 等）忽略；逐字时间标签（`<mm:ss.xx>`）去掉，只留文字。
  - 空文本的时间行是**结束标记**：它让上一句在此刻结束，自身不成为歌词行。
  - 每句的结束 = 下一句的开始（或下一个结束标记）；最后一句取「开始 + 5 秒」与歌曲时长中较小者。
  - 按时间排序后使用；同一时刻的多句保持文件顺序。
- 校验（上传时执行，失败返回明确原因，不落盘）：UTF-8（接受 BOM）；大小 ≤ 200 KB；至少一句歌词；没有任何时间戳的纯文本直接拒绝；时间不能为负、不能晚于歌曲时长 + 1 秒。
- 解析后的结构：`LyricLine { text: str, start: float, end: float }`，单位秒。

### 3.2 时间轴（`studio.timeline`）

- `Timeline.lyrics` 由预留的 `list[Any]` 改为 `list[LyricLine]`（有类型）。这是对「`timeline` schema 不变」的唯一例外，理由是该字段一直是预留，此前没有任何使用者。
- `produce` 的歌曲形态加载器读取 `music/lyrics.lrc`：按 `music/range.json` 截取（与 `beat` 事件同一套规则），把时间换成相对区间起点，丢弃区间外的句子，跨界的句子裁到区间内；没有文件则 `lyrics == []`。
- 歌词参与时间轴哈希：改歌词会让依赖时间轴的预览与成片重新校验。
- 讲解类、合成短片不读歌词。

### 3.3 运行时（`runtime.js`）

新增两个取数接口，沿用 `hit`/`energy` 的风格（时间是 `t` 的纯函数，镜头局部时间）：

- `env.lyrics`：本镜头内的歌词行数组，每项 `{ i, text, start, end }`（`i` 为整首歌内的序号，`start`/`end` 是镜头局部时间，可超出镜头）。
- `env.lyric()`：当前时刻正在唱或最近刚唱完（间隔 ≤ 1 秒内）的那一句，返回 `{ i, text, start, end, progress }`（`progress` 为 0–1）；没有则 `null`。

没有歌词时 `env.lyrics` 为空数组、`env.lyric()` 为 `null`，不抛错（与 `hit` 在 MV 无命名事件时的中性处理一致）。

## 4. 「创意与要求」（`concept`）

- **上传**：歌曲上传区旁加「歌词（.lrc）」上传，规则同歌曲——只在「创意与要求」进行中显示（避免 TD-81 的同类问题）；上传接口 `POST /projects/{id}/music/lyrics`，与歌曲接口一样检查「项目正在运行中的一轮」和并发上传；成功后写 `music/lyrics.lrc`。再次上传覆盖。提供 `DELETE` 删除歌词。
- **分析**：`analyze_music` 的结果文本附歌词概况：行数、覆盖时长占比、最长的无歌词间隔、歌词是否超出歌曲。分析本身不依赖歌词。
- **简报**：`concept` 的章节在有 `music/lyrics.lrc` 时多一章 **「歌词意象」**（紧跟「视觉母题」之后）。内容：
  - 逐句或逐段写「歌词 → 画面隐喻 → 屏幕上出现的关键字 → 卡在哪个拍点（或哪种节拍事件）」；
  - 统一的**视觉语言**（底色、强调色、字体风格、线条与网格）——这一条写在「视觉母题」里，「歌词意象」引用它；
  - 对叙事类歌词（有明确情节）可按段落写，对抒情类歌词（意象零散）按句写。
- `check_concept`：有歌词且「歌词意象」缺失或为空时报错；「歌词意象」里至少要逐字引用一句 LRC 里真实存在的歌词（防止整章都是编造的，不要求覆盖每一句）。无歌词时该章节不要求。
- 负责人确认简报即确认意象；`produce` 之后发现意象不合适，走 `suggest_upstream_change` 回到 `concept` 改。

## 5. `produce`

- `prepare_turn`：有歌词时多拷一个范例脚本 `lyrics-techniques.js`（`stages/common/scenes/exemplar/`），演示：底部字幕条（跟随 `env.lyric()` 的 `progress`）、关键字随拍点放大、数字滚轮、曲线绘制、终端打字、整屏大字闪出。全部是时间的纯函数，并说明范例不是模板。无歌词时不拷，不占上下文。
- 提示词新增「歌词」章节，仅在有歌词时适用：
  - 每句歌词至少对应一个画面或关键字动画；意象以简报「歌词意象」为准，不自行改题；
  - 文字出现与消失的时间用 `env.lyric()`/`env.lyrics`，不写死秒数；强调用 `env.hit('beat')`/`'downbeat'`；
  - 镜头划分建议跟歌词乐句走，不要按能量曲线把 5 分钟只切成 6 个；
  - 字幕样式、是否加英文，按简报来。
- **预览采样**：有歌词时，`render_preview_html` 的采样时间加入各句歌词的起始时刻（均匀抽样，仍受 16 张上限；与「稀有事件」「能量峰值」采样合并去重），让模型看到「这句歌词出现时画面是什么」。
- **校验**：`validate_scenes_html` 在有歌词时，如果没有任何场景脚本引用 `env.lyric` 或 `env.lyrics`，给警告（不拦）；不检查字幕是否真的画出来，那是预览图的事。
- **定稿与成片**：不新增阻塞条件。成片渲染不需要改：歌词随时间轴 JSON 进入页面。`final.json` 记录 `lyrics_hash`（歌词内容哈希），便于核对成片用的是哪一版歌词。

## 6. 前端

- 歌曲上传区增加歌词上传（`.lrc`，同样只在「创意与要求」进行中显示）；已上传时显示「更换歌词」「删除歌词」与行数。
- 「配乐」标签的分析摘要下新增「歌词」块：每行「时间 + 文字」，点击跳转播放位置；未上传时不显示。
- 能量曲线上叠加歌词起始位置的短刻度（可选，计划里作为独立小项）。

## 7. 事实来源与哈希

| 项 | 内容 |
|---|---|
| `music/lyrics.lrc` | 上传接口写入，工具托管；`concept` 的 `artifact_dirs` 已含 `music`，换歌词和换歌一样会让 `produce` 变 stale |
| 时间轴 | `Timeline.lyrics` 来自解析结果，哈希已含在时间轴哈希里 |
| 成片 | `final.json.lyrics_hash` |

## 8. 已知问题与风险

- **歌词时间的准确度取决于用户的 LRC**：很多网上的 LRC 偏移 0.3–1 秒，或间奏处有错行。系统不修正，只提供 `[offset:]` 与预览自查；偏差大时由用户换文件或加偏移。
- **模型听不到**：它只能靠预览图判断「这句歌词出现时画面对不对」。拍点对不对、情绪对不对仍要用户试听。
- **意象质量依赖 `concept`**：歌词意象写得空泛，成片就空泛；这一步是人确认的最后一道关，提示词要给足例子。
- **范例脚本的占用**：范例越多模型越会照抄。只放一个，并明确不是模板。
- **歌词里的版权**：歌词与歌曲一样是用户自己的文件，不进仓库；冒烟的歌词用环境变量指定路径。
- **TD-80、TD-81**（produce 评审登记）在本设计里被部分缓解：歌词上传区限定在 `concept` 进行中；后端按阶段状态拒绝上传仍未做，维持原登记。

## 9. 测试

- **LRC 解析**（纯函数，表驱动）：单时间戳、多时间戳、`[offset:]` 正负、元信息标签、逐字标签、空行结束标记、乱序、同刻多句、BOM、CRLF、无时间戳纯文本拒绝、超大文件、时间超出歌曲、空文件。
- **时间轴**：截取区间（区间内、跨界裁剪、区间外丢弃）、无歌词文件时为空、歌词变化使哈希变化、无歌词时与改动前的哈希一致（回归）。
- **运行时**：`env.lyrics`/`env.lyric()` 的边界（句首、句尾、间隔、第一句之前、最后一句之后、无歌词中性值），真实 Chromium 的 `slow` 用例。
- **concept**：有歌词时「歌词意象」必填、引用至少一句真实歌词的校验、无歌词时不要求。
- **produce**：预览采样含歌词起始、校验警告、`prepare_turn` 有无歌词的范例拷贝、提示词关键规则（含「不要写死秒数」）。
- **接口**：上传成功、非 UTF-8、纯文本、超限、并发、项目忙、非 MV 项目 404、删除；前端上传区的显示条件与歌词列表。
- **真实冒烟**：MV 冒烟加载歌词文件（`STUDIO_SMOKE_LRC`，缺失则跳过歌词部分并记录为未验证）；检查简报含「歌词意象」、场景脚本引用 `env.lyric`、成片通过；对照预览帧核对「歌词句首时画面是否对应」。
- **L4**：浏览器里走一遍歌词上传、替换、删除、列表跳转。

## 10. 实施

一个计划，大致顺序：LRC 解析与 `LyricLine` → 时间轴与运行时 → 上传接口与 `analyze_music` 概况 → `concept` 章节与检查 → `produce` 提示词、采样、校验、范例 → 前端 → 文档与冒烟。每个任务测试先行，完成后 `make check` 为绿再提交。计划写在 `docs/plans/active/`，设计批准后再写。
