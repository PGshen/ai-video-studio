# 0024：没有沙箱时默认不执行 agent 的命令，开关显式放开

## 背景

agent 能执行三类命令或代码：Claude CLI 的 Bash（Windows 上还有 PowerShell）、OpenAI 原生 Shell，以及 `render_music` 运行 agent 写的合成配乐脚本。macOS 上三者都在沙箱里：Claude 用 CLI 自带的 sandbox，另外两个用 Seatbelt（`sandbox-exec`），拒读仓库根、数据目录和家目录里的敏感目录，并且断网（ADR 0009）。

原生 Windows 上没有可用的读隔离（设计 §4.1）：Claude Code 官方说明原生 Windows 上命令不经沙箱运行；Codex 的 Windows sandbox 只限写和断网，也不是 Agents SDK 能复用的库；自己实现 AppContainer、受限 token 或转发到 WSL2，工作量和风险都远大于本项目其他部分。

我们关心的主要风险是**提示注入后读取敏感文件，再把内容发出去**。默认的 `tools` 联网模式下只有选题和头脑风暴两个阶段能联网，`fetch_url` 还受"URL 来源"限制（ADR 0010）。所以没有沙箱时，剩余的主要风险是：在这两个阶段被注入，然后通过命令自己发网络请求（例如 `curl`）。

## 决定

- 新模块 `agent/exec_policy.py`：`exec_mode(*, platform, sandbox_available, allow_unsandboxed) -> "sandboxed" | "unsandboxed" | "disabled"`。有沙箱就是 `sandboxed`，开关被忽略；没有沙箱时开关关闭是 `disabled`，打开是 `unsandboxed`。**macOS 上开关不起作用**：即使 `sandbox-exec` 缺失也只会是 `disabled`，不能用开关关掉隔离。
- **每个执行点各自传入"本执行点有没有沙箱"**，`exec_mode` 只做决定：Claude 看 CLI 自带的 sandbox（macOS、Linux、WSL2 有），OpenAI Shell 和 `render_music` 看 Seatbelt（只有 macOS）。Linux 不在正式支持范围内，但 Claude 在 Linux 上走 `sandboxed`，另外两个照旧失败关闭。
- 开关：环境变量 `STUDIO_ALLOW_UNSANDBOXED_EXEC`（默认 `false`）；设置页可以覆盖（`settings` 表的 `allow_unsandboxed_exec` 键，`effective_allow_unsandboxed_exec`：界面设置 > 环境变量 > 默认值），"清除界面设置"后回到环境变量。**每轮开始时读一次**，放进 `TurnContext` 和 `ToolContext`，本轮之内不变；配乐渲染接口（界面上的"渲染"按钮）每次请求读一次。
- 三种模式下各执行点的行为（设计 §4.3）：
  - Claude：`sandboxed` 照旧；`disabled` 从内置工具里去掉 `Bash`，`disallowed_tools` 放 `Bash` 和 `PowerShell`，**不传 `sandbox`**（传 `enabled` 加 `failIfUnavailable` 会让 Windows 上的 CLI 直接拒绝启动，整轮失败）；`unsandboxed` 放行 `Bash`（Windows 上 CLI 用 Git Bash 执行）和 Windows 上的 `PowerShell`，不传 `sandbox`。读写 hook 和轮末 `guard` 在所有模式下都保留。
  - OpenAI 原生 Shell（只在官方 API 上提供）：`disabled` 不提供；`unsandboxed` 提供，executor 不包裹 `sandbox-exec`，命令交给 `/bin/sh`，Windows 上交给 Git Bash（`CLAUDE_CODE_GIT_BASH_PATH` 或 `git` 旁边的 `bin/bash.exe`，绝不用 WSL 的 `bash.exe`）；密钥变量过滤、超时、输出上限、结束时清理进程树照旧。
  - `render_music`：`disabled` 返回错误，说明这台机器上没有沙箱，并指出设置页的开关；`unsandboxed` 直接运行，环境变量白名单、超时、事后的产物大小检查照旧。
  - 歌曲分析是项目自己的代码，不受开关影响。
- 每轮在 `turns.usage.exec_mode` 记下本轮**最弱执行点**的模式（`host_exec_mode`：Seatbelt 可用的平台比 Claude sandbox 少，以它为准），界面据此给 `unsandboxed` 的轮次显示"命令未隔离"标记（计划 T6）。

## 考虑过的其他方案

- **Windows 上不提供任何命令执行，也不给开关**：最安全，但短片形态离不开 `render_music`，Windows 上就做不了短片；负责人希望在知情的前提下能用。
- **默认打开，界面提示风险**：和 ADR 0009"失败关闭"的原则冲突；提示很容易被忽略。
- **自建 Windows 读隔离**（AppContainer、受限 token、Windows Sandbox 虚拟机、转发到 WSL2）：见背景，不做。以后 Claude Code 或 OpenAI 提供 Windows 读隔离时，只要在对应执行点把 `sandbox_available` 改成真就能接上。
- **开关只管 Shell**（讨论时叫 `STUDIO_UNSANDBOXED_SHELL`）：合成配乐脚本同样是 agent 写的代码，风险相同，一个开关一起管，名字改成 `ALLOW_UNSANDBOXED_EXEC`。

## 影响

- macOS 的行为、测试和安全性不变；Windows 上默认和以前的"非 macOS"一样失败关闭。
- 打开开关之后的剩余风险：命令能读到本机任何当前用户可读的文件，也能联网；写入工作区之外的文件不会被 `guard` 还原（`guard` 只管工作区）。Windows 上命令退出后留在后台的进程清理不到，可能在轮末 `guard` 之后才改工作区（TD-92，2026-10-10 补记）。设置页的说明文字写明这一点。
- `ClaudeRuntime`、`OpenAIRuntime` 多了 `platform` 构造参数（测试用）；`render_music` 用模块属性 `exec_platform`（同 `sandbox_wrapper`，测试里替换）。
- Windows 上 CLI 的真实工具名（`PowerShell`）、`disallowed_tools` 是否生效、不传 sandbox 时的表现，要在计划 T10 实测；和这里的假设不一致时走升级流程。
