## 背景

所有项目都要从选题池的卡片创建，并按阶段推进（讲解 `topic → narrative → (music) → animation_html`，短片与 MV `concept → produce`）。"给一个题目直接出讲解片""临时做一条短片"这类用法不需要选题、阶段、定稿与上游约束，只要一个对话里做完，并保留实时预览与成片。

约束：阶段协议（`agent/stage.py`）的 `system_prompt()`、`tools()`、`write_scope()` 不带项目参数；各阶段之间互不 import；预览与成片按项目类型从工作区顶层读固定位置的文件。

## 决定

1. **项目类型加 `mode: staged | free`**，创建时选、之后只读；老项目没有该字段时按 `staged`。形态（讲解 / 短片 / MV）照旧由 `narration`、`music_source` 决定，预览与成片不改。
2. **两个自由阶段，而不是一个 `free`**：`free_explainer`（有旁白）、`free_produce`（无旁白；按 `music/source.*` 分短片与 MV，与 `produce` 相同）。流水线只有这一个阶段。原因是阶段协议不带项目参数，一个阶段名只能有一套提示词与工具；沿用"差异大的拆阶段、差异小的按工作区文件分流"的现有做法，不改协议。
3. **可写范围是整个工作区**：`writable=["*"]`（`fnmatch` 的 `*` 匹配 `/`）；工具生成的文件、上传的歌曲与歌词、项目风格 `style/**` 列进 `tool_managed`。`WriteScope` 没有排除列表，借越界防线把它们还原为本轮开始时的内容，`style/` 因此实际只读。联网，没有上游（`reads()=[]`），所以没有 stale 与回退建议；定稿只发生在「成片定稿」。
4. **工具的时间轴来源查表**：`stages.common.timeline_source` 记录"阶段 → 来源"（`upstream` / `live_silent` / `live_narrated`），取代散落在工具里的 `ctx.stage == "produce"` 分支；`free_explainer` 即时从顶层 `narrative/` 构建时间轴，`render_music` 的 `base_hash` 与 worker 的口径一致。
5. **提示词片段化**：格式与契约类段落从原阶段提示词按 `## ` 标题切出，放在 `stages/common/prompts/`；多阶段提示词改为拼接，结果与拆分前逐字相同；自由阶段引用同一批片段，再加自己的开场白与 `free-mode` 公共片段。
6. **项目说明文件**：创建自由项目时生成 `notes/project.md`（形态、成片需要的文件），因为阶段只拿得到工作区路径，agent 靠它知道是否带背景乐、是短片还是 MV。

## 考虑过的其他方案

- **多阶段全部解锁、放宽写入范围**：几乎不用写新阶段，但定稿、stale、`upstream/` 机制仍在运行，阶段之间互相覆盖文件会让状态混乱，也不是"一个环节"。不选。
- **脱离阶段系统的裸项目**：概念最干净，但会话、渲染任务、成片定稿、前端路由都以阶段为单位，改动遍布全栈，收益与本方案相当。不选。
- **一个 `free` 阶段 + 扩展阶段协议（把项目类型传进 `system_prompt`/`tools`）**：改动公共接口，影响所有阶段与 TurnRunner。不选。
- **创建时不选形态、由产物推断**：最接近"随便做"，但要让时间轴加载、worker、预览接口摆脱项目类型，还要处理形态半途改变。负责人选择创建时选形态。

## 影响

- 好处：预览、成片、worker、时间轴零改动；契约类提示词只维护一份；工具的时间轴来源集中在一张表里。
- 代价：`free_produce` 在还没有歌曲时分不清短片与 MV，靠 `notes/project.md` 与提示词说明；agent 可能删掉这份说明（可回滚）。片段里沿用的两处说法对自由阶段不准确（叙事格式里的 `.py`、`STUDIO_TIMELINE` 指向 `upstream/timeline.json`），由自由阶段的开场白纠正。
- 之后：新增阶段时，若工具要即时构建时间轴，在 `timeline_source` 表里登记；改格式契约时改 `stages/common/prompts/` 的片段，多阶段与自由阶段一起生效。
