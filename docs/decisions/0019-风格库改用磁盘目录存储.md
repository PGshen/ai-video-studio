# 0019：风格库改用磁盘目录存储，AI 对话改的是草稿

## 元信息

| 项 | 值 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-04 |
| 相关 | [风格库重构设计](../superpowers/specs/2026-10-04-style-library-redesign-design.md)、[计划 style-library](../plans/completed/style-library.md)、取代 [ADR 0011](0011-风格库采用skill形态目录.md) 的存储方式、[ADR 0004](0004-原生工具优先.md) |

## 背景

ADR 0011 把风格存进 SQLite 的 `style_presets` 表（`content`、`reference_files`、`exemplars` 三个文本/JSON 列）。现在要给风格库加 AI 对话：让 agent 直接改风格。表里的 JSON 列没法给 agent 用原生 Read/Edit/Write 工具；每轮把整份风格从前端提交、渲染成临时目录、再取回，既绕又容易出错。`STYLE.md` 的 frontmatter 里本来就有 `name` 和 `description`，数据库里还有一份同名列，两处容易漂移。

## 决定

- 风格存成磁盘目录，SQLite 不再保存风格：正式版本在 `data/styles/<id>/`（`STYLE.md`、`references/`、`exemplars/`），草稿在 `data/style-drafts/<id>/`。目录结构、文件命名和引用约定沿用 ADR 0011，创建项目时仍然复制进项目 `style/`，复制后与风格库脱钩。
- 名称、简介、分类都写在 `STYLE.md` 的 frontmatter（`name`、`description`、`category`），不再有独立的数据库列；默认风格仍是 `settings.default_style_preset_id`。
- 编辑走草稿：用户在编辑器里改的、agent 在对话里改的，都是草稿目录；「保存」时校验通过才用原子替换覆盖正式版本，「放弃修改」删除草稿。没有历史和回滚。
- 新增纯能力模块 `studio.styles`（只依赖 `config`），放目录布局、校验和存储，使 `db`（旧表导出、导入脚本）、`api`、`agent` 都能使用。
- 风格对话是一个 `style` 阶段的会话，`sessions.subject_id` 记录它属于哪套风格；agent 的工作目录就是该风格的草稿目录。
- 旧表数据一次性导出成目录（目录名沿用旧 id，没有 frontmatter 的旧行用数据库列合成），核对数量后由迁移删表。

## 考虑过的其他方案

- **SQLite 只存元数据和目录路径**：`name`/`description` 与 frontmatter 重复，两个事实来源会漂移；去掉重复后剩下的只是 id 和路径，不如直接扫描目录。
- **每次发消息时前端提交完整草稿，后端渲染成临时目录**：要传整包内容、轮次结束后再取回，草稿也只存在于前端，刷新就丢。
- **自建 read/write 工具操作服务端草稿**：agent 没有原生 Edit，大文件只能整体重写，违背 ADR 0004。
- **agent 直接改正式版本，用快照回滚**：需要为风格另建版本历史和回滚界面，也要处理用户有未保存修改时的写入冲突；草稿方案不需要。

## 影响

- [架构设计](../design/2026-09-26-architecture.md) §3.1 对 `style_presets` 表的描述过时；按红线不修改该文件，以本 ADR 和 `docs/ARCHITECTURE.md` 为准。
- `/api/style-presets*` 由 `/api/styles*` 取代；旧项目导入脚本改为写目录。
- 升级前要备份 `data/studio.db`：旧表导出成目录之后由迁移删除，没有降级。
- 风格的读写不再有数据库事务：靠「先写临时目录再 rename」保证保存是原子的。
- 同一套风格有对话轮次运行时，草稿的写入、保存、放弃和删除会被拒绝（409）。
